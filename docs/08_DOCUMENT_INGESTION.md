# 문서 등록과 관계 추출 실습

문서를 등록하면 사내 LiteLLM이 서비스·팀·관계 후보를 추출합니다. 사용자가 미리보기에서 확인하고 수정한 뒤 저장하면 Neo4j에 문서와 관계가 함께 들어갑니다. 저장한 데이터는 다음 GraphRAG 조회부터 사용됩니다.

**관계 추출은 제안 단계입니다.** 추출 버튼을 누르는 것만으로 DB가 바뀌지는 않습니다. 저장 버튼을 눌러 확인한 결과만 반영합니다.

이미 저장한 문서를 고치거나 지우려면 [문서 관리 페이지](http://127.0.0.1:8000/documents/manage/)를 사용합니다. 새 문서 등록과 기존 문서 개정의 차이는 [문서 관리 가이드](09_DOCUMENT_MANAGEMENT.md)에서 설명합니다.

## 1. 준비하고 페이지 열기

먼저 [README](../README.md)에 따라 Neo4j 연결과 예제 적재를 완료하고, [GraphRAG 가이드](07_GRAPHRAG_GUIDE.md#2-사내에서는-기존-litellm-연결하기)에 따라 사내 LiteLLM을 연결합니다. 개인 PC에서는 같은 기능을 Ollama로 확인할 수 있습니다. `LLM_PROVIDER`에 지정한 제공자를 사용하며, 실패했다고 다른 외부 모델에 자동으로 전송하지 않습니다.

기존 `.env`에 다음 설정을 확인합니다.

```dotenv
LLM_PROVIDER=litellm
LITELLM_BASE_URL=http://YOUR_INTERNAL_LITELLM_HOST:4000/v1
LITELLM_MODEL=YOUR_DEPLOYED_MODEL_ALIAS
LITELLM_API_KEY=YOUR_APPLICATION_KEY
LLM_EXTRACTION_MAX_TOKENS=3000
DJANGO_SECRET_KEY=YOUR_PRIVATE_RANDOM_VALUE
```

위 값은 안내용 자리표시자입니다. 사내 서버 주소·모델 별칭·키는 회사 환경에서 입력합니다. `LLM_EXTRACTION_MAX_TOKENS`는 관계 추출 결과의 최대 출력 토큰 수이며, 짧은 GraphRAG 답변의 토큰 설정과 별개입니다.

로컬 Ollama의 추출 문맥 크기는 `OLLAMA_EXTRACTION_NUM_CTX=32768`이 기본값입니다. 긴 원문과 구조화 결과를 함께 처리하기 위한 설정이며, 일반 답변의 `OLLAMA_NUM_CTX`와 별개입니다. 메모리가 부족하면 원문을 작은 문서로 나누고 모델·문맥 크기를 함께 조정합니다.

`DJANGO_SECRET_KEY`는 미리보기의 원본 문서와 유효기간을 확인하는 서명에 사용합니다. 다음 명령으로 생성한 값을 본인의 `.env`에 한 번 입력하고, 실제 값은 Git에 올리지 않습니다.

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

키를 비워 두면 서버가 시작될 때 임시 키를 만듭니다. 이 경우 Django 재시작 후에는 이전 미리보기를 저장할 수 없어 다시 추출해야 합니다. 같은 서버를 여러 프로세스로 실행할 때도 동일한 비공개 키가 필요합니다.

설정을 바꿨다면 Django를 재시작합니다.

```powershell
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

[문서 등록 페이지](http://127.0.0.1:8000/documents/)를 엽니다. GraphRAG 화면의 문서 등록 링크로도 이동할 수 있습니다.

## 2. 작은 문서로 먼저 실습하기

제목에 `배송 서비스 운영 안내`, 본문에 아래 문장을 입력합니다.

```text
배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다.
```

출처에는 원본 문서의 위치나 문서 번호를 선택적으로 적습니다. 예를 들어 `internal-docs/delivery-guide`처럼 나중에 원문을 식별할 수 있는 값을 사용합니다. 출처에 경로나 URL을 입력해도 서버가 그 위치를 찾아 읽지는 않습니다. **본문 입력란에 있는 내용이 저장할 원문**입니다.

파일로 입력하고 싶다면 UTF-8로 저장한 `.txt` 또는 `.md`를 선택합니다. 브라우저가 파일을 읽어 본문 입력란에 넣고, 추출 요청 시 제목·본문·출처를 Django로 보냅니다. PDF·Word 파일과 OCR은 현재 지원하지 않습니다.

| 항목 | 입력 범위 |
| --- | --- |
| 제목 | 필수, 최대 200자 |
| 본문 | 필수, 최대 12,000자 |
| 출처 | 선택, 최대 500자 |
| 파일 형식 | UTF-8 `.txt`, `.md`, 최대 64KB |
| 한 번의 검토 대상 | 노드 최대 30개, 관계 최대 60개 |
| 관계별 근거 문장 | 원문의 일부, 1~1,000자 |

관계 추출을 실행합니다. 모델이 문서와 기존 서비스·팀 목록을 읽고 후보를 반환하므로 첫 실행에는 모델 로딩 시간이 추가될 수 있습니다.

## 3. 노드와 관계 미리보기 확인하기

노드는 그래프에 저장할 **대상**이고, 관계는 대상 사이의 **연결**입니다. 같은 대상을 새 노드로 또 만들지 않도록 기존 노드 목록을 먼저 확인하세요. 모델 결과가 아래 예시와 정확히 같을 필요는 없습니다. 미리보기에서 사람이 올바른 결과로 수정합니다.

| 대상 | 사용할 ID 예시 | 확인할 내용 |
| --- | --- | --- |
| 배송 서비스 | `delivery-service` | 예제 DB에 없으므로 새 `Service` 후보 |
| 주문 서비스 | `order-service` | 기존 서비스를 재사용 |
| 물류팀 | `logistics-team` | 예제 DB에 없으므로 새 `Team` 후보 |

ID는 노드의 고유 식별자입니다. `주문 서비스`, `주문 API`, `Order Service`가 같은 시스템을 뜻한다면 같은 `order-service`를 사용해야 합니다. 이름만 비슷한 다른 서비스라면 ID를 구분합니다. 새 ID는 소문자 영문·숫자로 시작하고, 소문자 영문·숫자·하이픈·밑줄로 최대 100자까지 작성합니다. `delivery-service`처럼 짧게 정하면 관리하기 쉽습니다. 같은 종류의 노드가 동일한 이름으로 이미 있으면 서버가 기존 ID를 재사용할 수 있습니다. 기존 이름의 공백·대소문자 차이는 정규화하여 비교하지만, 서로 다른 별칭의 의미까지 판별하는 기능은 아닙니다.

이번 문서에서 확인할 관계는 다음과 같습니다.

| 시작 | 관계 | 도착 | 뜻 |
| --- | --- | --- | --- |
| 등록하는 문서 | `DESCRIBES` | 배송 서비스 | 문서가 이 서비스를 설명함 |
| 배송 서비스 | `DEPENDS_ON` | 주문 서비스 | 배송이 주문에 의존함 |
| 배송 서비스 | `OWNED_BY` | 물류팀 | 물류팀이 배송을 담당함 |

관계의 **방향**을 확인합니다. 위 문장은 배송이 주문에 의존한다는 뜻이며, 주문이 배송에 의존한다는 뜻은 아닙니다. `OWNED_BY`는 서비스에서 팀으로 향하고, `DESCRIBES`는 현재 문서에서 서비스로 향합니다.

노드와 관계를 추가·수정·삭제하거나 저장 대상에서 제외할 수 있습니다. 제외한 노드를 가리키는 관계도 정리해야 합니다. 기존 노드를 선택한 경우 저장 과정에서 그 노드의 이름·설명을 덮어쓰지 않습니다. 잘못된 기존 정보의 수정은 이 등록 화면과 별도의 관리 작업입니다.

각 관계에는 **원문에 실제로 있는 근거 문장**을 넣습니다. 이번 예시에서는 `배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다.`를 그대로 사용할 수 있습니다. 근거는 원문의 부분 문자열이어야 하므로 띄어쓰기·줄바꿈까지 원문에서 복사하는 것이 가장 간단합니다. 모델의 설명이나 사람이 새로 쓴 요약을 근거 칸에 넣으면 검증에 실패할 수 있습니다.

모델이 연결 대상을 잘못 선택하거나 본문에 없는 근거를 제안하면 미리보기에 경고를 표시합니다.
경고는 추출 당시 결과에 대한 안내입니다. 해당 관계를 수정하거나 저장 대상에서 제외하세요.
저장할 때는 선택한 관계만 다시 검사하며, 잘못된 방향·종류나 원문에 없는 근거가 남아 있으면 저장하지 않습니다.

다음 표현은 특히 확인하세요.

- `향후 결제 서비스를 호출할 예정`: 현재 의존 관계인지 검토합니다.
- `A가 B를 호출하지 않는다`: 호출 관계로 저장하면 안 됩니다.
- `과거에는 플랫폼팀이 담당했다`: 현재 담당팀인지 확인합니다.
- `주문 서비스와 주문 관리 서비스`: 같은 대상인지 이름만으로 판단하지 않습니다.

원문에 해당 표현이 존재한다는 검사는 **문장이 관계를 뒷받침하는지까지 보장하지 않습니다.** 미리보기에서 의미를 판단하는 역할은 사용자에게 있습니다.

## 4. 확인한 결과 저장하기

검토를 마친 후 확인 체크박스를 선택하고 **검토한 내용 저장하기**를 누릅니다. 문서, 새 노드, 선택한 관계, 관계별 근거 기록이 하나의 Neo4j 트랜잭션으로 저장됩니다. 오류가 발생하면 해당 저장 작업의 일부만 남기지 않고 되돌립니다.

저장 시 다음 규칙을 적용합니다.

- 관계 유형은 `DESCRIBES`, `DEPENDS_ON`, `OWNED_BY`만 허용합니다.
- 문서에서 서비스로 향하는 `DESCRIBES` 관계가 최소 1개 필요하고, 저장할 모든 노드는 관계에 연결되어야 합니다.
- 기존 서비스와 팀은 ID로 재사용하며 기존 속성을 변경하지 않습니다.
- 서비스에 다른 담당팀이 이미 있으면 `OWNED_BY` 충돌로 저장을 거부합니다. 기존 담당팀을 자동으로 교체하지 않습니다.
- 이미 존재하는 동일한 관계는 중복 생성하지 않고, 이번 문서의 근거를 별도로 기록합니다.
- 같은 미리보기의 동일한 저장 요청을 재시도해도 문서가 중복 생성되지 않습니다. 새로 추출한 요청은 별도 문서 등록이며, 같은 본문 전체를 비교하는 중복 제거 기능은 없습니다.
- **새 문서 등록** 화면에서 후보를 삭제하거나 제외해도 이미 DB에 있는 노드·관계를 삭제하지 않습니다. 기존 문서 수정 화면에서는 해당 문서의 이전 관계 근거를 새 검토 결과로 교체합니다.

미리보기는 추출 후 **1시간** 동안 저장할 수 있습니다. 원문 제목·본문·출처를 바꾸면 기존 미리보기를 그대로 저장하지 않고 다시 추출합니다. 페이지를 새로고침하거나 닫기 전에는 미저장 원문과 수정 내용을 별도로 보관하세요. 초안 목록을 서버에 보관하는 기능은 없습니다.

## 5. GraphRAG에서 바로 확인하기

저장 완료 화면의 GraphRAG 링크로 이동하면 연결된 서비스를 기준으로 조회할 수 있습니다. 또는 [GraphRAG 페이지](http://127.0.0.1:8000/graphrag/)를 새로 열고 서비스 선택에서 `배송 서비스`를 선택합니다.

문맥 조회로 아래 질문을 실행합니다.

```text
배송 서비스의 담당팀과 의존 서비스, 관련 문서를 알려줘.
```

검색 근거에서 `배송 서비스 → 물류팀`, `배송 서비스 → 주문 서비스`, 방금 등록한 문서 제목과 본문을 확인합니다. **근거만 조회**는 LLM 없이도 확인할 수 있고, 답변 생성은 검색한 근거를 선택한 LLM에 전달합니다.

이번에는 `주문 서비스`를 선택하고 영향 분석을 실행해 보세요.

```text
주문 서비스에 문제가 생기면 어떤 서비스가 영향을 받을 수 있어?
```

새로 저장한 방향대로 `배송 서비스`가 영향 후보에 포함되어야 합니다. 이 결과는 관계를 따라 찾은 후보이며 실제 장애 발생을 뜻하지는 않습니다.

GraphRAG는 요청할 때마다 Neo4j를 조회하므로 별도의 임베딩 생성이나 인덱스 재구축이 필요하지 않습니다. 같은 브라우저에서 같은 주소·포트로 연 GraphRAG 탭은 문서 변경 알림을 받으면 이전 답변·근거를 비우고 최근 검색을 다시 실행합니다. 새 LLM 답변은 **답변 생성**을 눌러 요청합니다. 다른 브라우저나 기기에서는 새로고침하거나 다시 조회하세요. 등록한 문서가 아무 질문에나 포함되는 것은 아니며, 선택한 서비스와 조회 범위에 연결된 문서를 검색합니다. 문맥 조회는 대상과 직접 의존 서비스, 영향 분석은 역방향 최대 5홉을 사용합니다.

## 6. 저장되는 데이터 이해하기

기본 업무 그래프에는 `:Lab:Document`, `:Lab:Service`, `:Lab:Team` 노드를 사용합니다. 문서의 `title`, `body`, `source`가 DB에 저장되고, 서비스와 팀은 확인한 관계로 연결됩니다.

관계의 근거를 나중에 확인할 수 있도록 `:Lab:Assertion` 노드도 저장합니다. 이 기록에는 원문 문서 ID, 시작·도착 대상 ID, 관계 유형, 근거 문장이 들어갑니다. **관계 하나를 여러 문서가 뒷받침할 수 있으므로**, 공유하는 관계와 문서별 근거를 구분해 보관합니다. GraphRAG 화면의 서비스·팀·문서 그래프와 Neo4j의 전체 `Lab` 노드 수가 다른 이유이기도 합니다.

개발자가 확인할 속성은 `document_id`, `source_id`, `target_id`, `relation_type`, `evidence`, `created_at`, `reviewed`이며 문서에서 `SUPPORTS` 관계로 연결합니다. 기존 예제의 11개 노드·12개 관계는 초기 데이터 수입니다. 문서 등록 후 전체 DB에는 새 업무 노드뿐 아니라 근거 기록과 저장 동시성 제어용 노드도 추가되므로 초기 수치와 같지 않습니다.

등록한 문서는 문서 관리 화면에서 개정하거나 삭제할 수 있습니다. 수정할 때는 이전 근거를 철회하고 새 검토 결과로 교체합니다. 삭제할 때는 해당 문서의 근거만 철회합니다. 앱이 문서 등록으로 만든 관계는 남은 근거가 없을 때 정리하고, 다른 문서가 뒷받침하는 관계와 예제·수동 관계는 보존합니다. 서비스·팀 노드는 유지합니다. 이전 버전에서 만들어져 생성 경로를 알 수 없는 관계의 처리와 자세한 규칙은 [문서 관리 가이드](09_DOCUMENT_MANAGEMENT.md#4-관계가-사라지거나-남는-기준)를 참고하세요.

## 7. 개발자를 위한 API와 처리 경계

| 메서드·경로 | 역할 |
| --- | --- |
| `GET /documents/` | 문서 등록·미리보기 화면 |
| `GET /api/documents/catalog/` | 기존 서비스·팀 후보 목록 |
| `POST /api/documents/extract/` | 원문 검증, LLM 관계 추출, 서명된 미리보기 발급 |
| `POST /api/documents/save/` | 검토 결과 검증 후 Neo4j에 저장 |

추출 요청은 `Content-Type: application/json`과 CSRF 토큰을 사용합니다.

```json
{
  "title": "배송 서비스 운영 안내",
  "body": "배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다.",
  "source": "internal-docs/delivery-guide"
}
```

저장 요청은 추출 응답의 `review_token`과 사용자가 검토한 `nodes`, `relations`를 전달합니다. 원본 문서는 서명된 토큰에서 확인하므로 저장 요청에 바꾼 본문을 넣어 원문 검증을 우회할 수 없습니다. 서명은 변조 확인용이며 암호화가 아닙니다. 원문과 토큰을 URL이나 외부 로그에 기록하지 않습니다.

추출 응답의 주요 형식은 다음과 같습니다. `document.id`와 `review_token`은 실제 응답에서 받은 값을 유지합니다.

```json
{
  "document": {"id": "doc-...", "title": "배송 서비스 운영 안내", "body": "...", "source": "..."},
  "nodes": [
    {"id": "delivery-service", "kind": "Service", "name": "배송 서비스", "description": "", "existing": false},
    {"id": "order-service", "kind": "Service", "name": "주문 서비스", "description": "...", "existing": true},
    {"id": "logistics-team", "kind": "Team", "name": "물류팀", "description": "", "existing": false}
  ],
  "relations": [
    {"source_id": "doc-...", "type": "DESCRIBES", "target_id": "delivery-service", "evidence": "배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다."},
    {"source_id": "delivery-service", "type": "DEPENDS_ON", "target_id": "order-service", "evidence": "배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다."},
    {"source_id": "delivery-service", "type": "OWNED_BY", "target_id": "logistics-team", "evidence": "배송 서비스는 주문 서비스에 의존하며 물류팀이 담당합니다."}
  ],
  "review_token": "실제 응답의 서명된 토큰",
  "warnings": [],
  "provider": "litellm",
  "model": "사내 모델 별칭"
}
```

저장 응답의 `document`에는 저장한 문서의 ID·제목·출처가, `service_ids`에는 연결한 서비스 ID 목록이 담깁니다. `created`가 `false`이면 동일한 검토 결과가 이미 저장되어 중복 생성하지 않은 경우입니다.

LLM에는 문서에서 추출할 구조를 요청하며 **LLM이 작성한 Cypher를 실행하지 않습니다.** 서버가 허용한 노드·관계 형식을 검증하고, 개발자가 작성한 Cypher에 값만 파라미터로 전달합니다. 저장 직전 기존 노드와 담당팀을 다시 확인하므로 미리보기 이후 DB가 바뀌면 충돌로 실패할 수 있습니다.

LiteLLM 연결은 `response_format`을 보내지 않고 JSON만 출력하도록 프롬프트로 요청한 뒤 Django에서 형식·근거를 검증합니다. 해당 옵션을 지원하지 않는 사내 모델·게이트웨이에도 연결하기 위한 선택입니다. JSON 출력에 실패하면 오류로 처리하며 임의로 관계를 만들어 보충하지 않습니다. 추후 사내 모델의 지원 여부가 확인되면 JSON 스키마 강제를 추가할 수 있습니다. [LiteLLM 구조화 출력과 모델 지원 확인](https://docs.litellm.ai/docs/completion/json_mode)

Ollama 연결은 `format: "json"`을 사용하고 같은 서버 검증을 거칩니다. 현재 구현은 완전한 JSON 스키마를 요청에 전달하지 않습니다. JSON 형식이 맞아도 추출한 관계의 의미가 맞는지는 별도 검토가 필요합니다. [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs)

## 8. 오류가 날 때

| 증상 | 해결 방법 |
| --- | --- |
| 추출 중 서버 연결·권한 오류 | `.env`의 제공자, LiteLLM 기본 주소, 모델 별칭, API 키를 확인 |
| 모델 결과가 JSON 형식에 맞지 않음 | 원문을 짧고 명확하게 나누어 다시 추출. 모델의 구조화 출력 성능도 확인 |
| 추출 결과가 중간에서 잘림 | `LLM_EXTRACTION_MAX_TOKENS`와 서버의 출력 제한 확인 후 재추출 |
| 근거 문장이 원문에 없다고 나옴 | 본문에서 문장을 직접 복사해 해당 관계의 근거에 입력 |
| 다른 담당팀이 이미 있다는 충돌 | 기존 팀을 재사용하거나 해당 후보를 제외. 팀 변경은 별도 관리 작업으로 처리 |
| 미리보기 만료·서명 오류 | 원문을 보존한 뒤 다시 추출. 재시작 때마다 생기면 `DJANGO_SECRET_KEY` 설정 확인 |
| 저장 후 응답을 받지 못함 | 동일한 미리보기·검토 내용으로 재시도. 새로 추출하기 전에 중복 등록 가능성을 확인 |
| GraphRAG에서 새 서비스가 안 보임 | 저장 성공 여부를 확인하고 GraphRAG를 새로고침 |
| 문서는 저장됐지만 질문에 안 나옴 | `DESCRIBES` 대상, 질문의 기준 서비스와 조회 범위를 확인 |

현재 구성은 로그인과 사용자별 권한이 없는 로컬 실습용입니다. 사내 공용 서비스에 붙일 때는 기존 Django 인증·문서 권한 체계와 저장·수정·삭제 권한을 연결하고, 문서 보존 기간과 승인·감사 정책을 정해야 합니다. PDF/DOCX 파싱, 대량 적재, 청크·벡터 검색은 별도 확장 범위입니다.
