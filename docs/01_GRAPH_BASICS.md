# 그래프 기본 개념과 이 프로젝트의 데이터 모델

## 1. 우리가 해결하려는 질문

> 주문 서비스에서 인증 문제가 생겼다. 어느 팀에 연락하고 어떤 운영 문서를 확인해야 할까?

이 질문에 답하려면 주문 서비스라는 이름만 찾는 것으로는 부족합니다. 어떤 서비스에 의존하는지, 그 서비스의 담당팀이 누구인지, 어떤 문서가 그 서비스를 설명하는지를 연결해야 합니다.

이 실습에서는 그 연결을 Neo4j에 저장합니다. GraphDB는 이러한 데이터를 저장·조회하는 DB의 종류이고, Neo4j는 그중 하나의 제품입니다.

## 2. 네 가지 기본 요소

| 요소 | 의미 | 예시 |
| --- | --- | --- |
| 노드(Node) | 한 개의 대상 | 인증 서비스, 플랫폼팀, 인증 운영 문서 |
| 라벨(Label) | 노드가 속하는 분류 | `Service`, `Team`, `Document` |
| 속성(Property) | 대상을 설명하는 값 | `id: 'auth-service'`, `name: '인증 서비스'` |
| 관계(Relationship) | 두 노드 사이의 의미 있는 연결 | `DEPENDS_ON`, `OWNED_BY`, `DESCRIBES` |

Neo4j의 이 모델을 **속성 그래프(Property Graph)**라고 부릅니다. 노드는 여러 라벨을 가질 수 있고, 관계는 방향과 하나의 관계 유형을 가집니다. 노드와 관계 모두 속성을 가질 수 있습니다. [Neo4j 속성 그래프 설명](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

이 예제의 인증 서비스는 `Lab`과 `Service`라는 두 라벨을 가집니다. `Lab`은 실습 데이터 전체를 묶는 분류, `Service`는 대상의 종류입니다. `Lab` 라벨은 데이터 접근 권한이나 DB 격리를 제공하는 기능은 아닙니다.

`(s:Lab:Service {id: 'auth-service'})`를 읽으면 “Lab이며 Service인 노드 중에서 id가 auth-service인 것을 찾아 s라고 부르겠다”라는 뜻입니다.

## 3. 전체 예제 데이터

| 서비스 ID | 서비스명 | 담당팀 | 직접 의존하는 서비스 |
| --- | --- | --- | --- |
| `order-service` | 주문 서비스 | 커머스팀 | 인증, 결제 |
| `auth-service` | 인증 서비스 | 플랫폼팀 | 없음 |
| `payment-service` | 결제 서비스 | 결제팀 | 인증 |
| `notification-service` | 알림 서비스 | 플랫폼팀 | 인증 |

각 서비스에는 운영 문서가 하나씩 연결됩니다. 예를 들어 인증 운영 문서의 ID는 `auth-guide`이고 원문은 `docs/samples/auth-guide.md`입니다.

그래프의 관계 방향을 문장으로 읽어보세요.

```text
(주문 서비스) ── DEPENDS_ON ──→ (인증 서비스)
(인증 서비스) ── OWNED_BY ────→ (플랫폼팀)
(인증 운영 문서) ── DESCRIBES ─→ (인증 서비스)
```

- `DEPENDS_ON`: 왼쪽 서비스가 오른쪽 서비스를 사용합니다.
- `OWNED_BY`: 왼쪽 서비스의 담당팀이 오른쪽 팀입니다.
- `DESCRIBES`: 왼쪽 문서가 오른쪽 서비스를 설명합니다.

문서를 찾을 때는 서비스에서 **들어오는 `DESCRIBES` 관계**를 따라가야 합니다. 저장된 관계 방향과 질의가 진행되는 방향은 구분해서 생각하세요. 쿼리에는 왼쪽 화살표도 쓸 수 있습니다.

```cypher
MATCH (service:Lab:Service {id: 'auth-service'})
      <-[:DESCRIBES]-(doc:Lab:Document)
RETURN doc;
```

## 4. 홉과 경로

관계 하나를 건너가는 이동이 **1홉(hop)**입니다. 연속된 연결을 경로(path)라고 부릅니다.

- 주문 → 인증: 1홉
- 주문 → 인증 → 플랫폼팀: 2홉이지만 관계 유형이 서로 다름
- 주문 → 결제 → 인증: `DEPENDS_ON` 관계만으로 2홉

“인증 장애 시 영향 후보”를 찾을 때는 인증 서비스에서 나가는 의존 관계가 아니라 **인증 서비스로 들어오는 의존 관계**를 따라갑니다. 주문·결제·알림이 후보입니다. 주문은 인증에 직접 의존하고, 결제를 거치는 경로도 있어 중복이 생길 수 있습니다. 예제 조회는 이를 정리해 서비스마다 한 번씩 반환합니다.

실습의 영향 조회는 최대 5홉으로 제한합니다. 탐색 범위를 무한하게 늘리면 데이터가 커졌을 때 많은 경로를 검사할 수 있습니다. 반대로 5홉보다 먼 의존 관계는 현재 결과에 포함되지 않습니다.

## 5. 무엇을 노드로 만들까?

팀을 서비스의 `team_name` 속성으로만 저장할 수도 있습니다. 이 예제는 다음 질문을 쉽게 하기 위해 팀을 별도 노드로 만들었습니다.

> 플랫폼팀이 담당하는 서비스를 모두 찾아줘.

여러 서비스가 같은 팀 노드를 공유하므로 같은 팀의 이름이 바뀌었을 때 한 노드의 값을 갱신할 수 있습니다. 문서도 여러 서비스와 연결할 가능성이 있으므로 별도 노드입니다.

반면 서비스의 간단한 설명처럼 독립적인 연결이 필요하지 않은 값은 속성으로 둡니다. 정답이 하나로 고정된 것은 아니며, **어떤 질문에 답하려는지**가 설계의 기준입니다.

## 6. ID, 이름, 제약 조건의 차이

- `id`: 코드가 대상을 식별하는 값입니다. 예: `auth-service`.
- `name`: 사람이 읽는 이름입니다. 예: `인증 서비스`.
- 유일성 제약 조건: 같은 라벨 안에서 동일 ID가 중복 저장되는 것을 방지합니다.

이름은 바뀌거나 중복될 수 있으므로 조회·적재의 기준은 ID로 둡니다. 이 프로젝트는 공통 `Lab` 라벨의 ID에 유일성 제약 조건을 적용합니다. 따라서 서비스·팀·문서를 통틀어 ID가 달라야 합니다. `seed_graph`는 제약 조건을 만들고 ID를 기준으로 노드를 합치거나 생성합니다. 수동 Cypher 학습용 제약 조건은 [queries/00_constraints.cypher](../queries/00_constraints.cypher)에 있습니다.

제약 조건이 있다고 관계의 내용이 사실로 검증되는 것은 아닙니다. 예를 들어 실제 담당팀이 바뀌었다면 데이터를 갱신해야 합니다.

## 7. Django와 Neo4j의 역할

일반적인 Django 프로젝트에서 `models.Model`과 ORM을 사용하면 관계형 DB 테이블을 다룹니다. 이 프로젝트에서는 Neo4j 공식 드라이버를 사용해 Cypher를 실행합니다.

| 역할 | 이 실습에서 담당하는 구성요소 |
| --- | --- |
| HTTP 요청을 받고 JSON 반환 | Django view |
| 터미널 명령 제공 | Django management command |
| Cypher와 조회 결과 처리 | Python의 그래프 조회 코드 |
| 연결·인증·트랜잭션 통신 | Neo4j 공식 드라이버 |
| 실제 그래프 저장과 검색 | Neo4j DB |

Django ORM이나 `migrate`가 Neo4j 노드를 생성하지 않습니다. 추후 기존 Django 서비스와 합칠 때는 관계형 DB와 Neo4j를 함께 사용할 수 있고, 각각의 책임과 동기화 방식을 따로 정해야 합니다.

## 8. 이 실습이 GraphRAG로 이어지는 지점

기본 CLI는 정해진 ID로 필요한 서비스·담당팀·문서를 찾습니다. 추가된 [GraphRAG 페이지](07_GRAPHRAG_GUIDE.md)는 질문의 서비스명 또는 사용자의 서비스 선택으로 대상을 식별하고, 조회 결과와 원문 내용을 사내 LiteLLM 서버에 전달해 답변을 생성합니다. 개인 PC에서 검증할 때는 로컬 Ollama를 선택할 수 있습니다.

문서 파일이 있다는 사실과 문서 내용을 모델이 자동으로 이해하는 것은 다른 단계입니다. 이 예제는 사람이 작성한 관계와 Markdown 원문을 적재합니다. 원문은 문서 노드의 `body`에 저장하고, 관련 문서 조회 시 함께 반환합니다. GraphRAG 답변은 이 근거를 사용합니다. 문서에서 관계를 자동 추출하거나 유사한 문장을 임베딩으로 찾는 과정은 포함하지 않습니다.

다음 단계에서는 **사용자가 볼 수 있는 문서만 조회하는 권한 처리**, 출처와 갱신 시점, 잘못 추출된 관계의 수정, 삭제된 문서 처리부터 설계하세요. 그래프에 담긴 정보의 품질이 검색 결과의 품질을 결정합니다.
