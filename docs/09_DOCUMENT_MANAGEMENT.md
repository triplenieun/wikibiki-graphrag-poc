# 문서 목록·수정·삭제 실습

문서 관리 화면에서 저장된 문서의 원문과 관계를 확인하고 수정·삭제합니다. 수정하거나 삭제한 결과는 Neo4j에 함께 반영되므로 다음 GraphRAG 검색부터 최신 상태를 사용합니다.

문서를 수정할 때는 **이번 문서가 주장하는 관계**를 교체합니다. 다른 문서가 같은 관계를 뒷받침한다면 그 관계는 남습니다. 이 구분이 문서 관리의 핵심입니다.

## 1. 문서 목록 열기

[README](../README.md)에 따라 Django와 Neo4j를 실행한 뒤 [문서 관리 페이지](http://127.0.0.1:8000/documents/manage/)를 엽니다. 서버가 다른 포트에서 실행 중이면 주소의 `8000`을 그 포트로 바꿉니다.

목록에서 제목·출처·관계 수·수정 시각을 확인하고 문서를 선택합니다. 제목·출처·문서 ID로 검색할 수 있습니다. 문서 등록 화면에서 저장한 문서는 수정·삭제할 수 있습니다. `seed_graph`로 적재한 예제 문서는 읽기 전용입니다. 예제 원문을 변경하려면 `docs/samples/`의 해당 파일을 고친 뒤 다시 적재합니다.

**문서 찾기**에 검색어를 입력하고 **검색**을 누릅니다. 목록은 한 번에 20개씩 표시하며 **이전·다음**으로 이동합니다. **목록 새로고침**으로 현재 목록을 다시 읽고, **상세 보기**에서 원문과 관계 근거를 확인합니다. 예제에는 **예제 · 읽기 전용** 표시가 있습니다.

처음이라면 [문서 등록 실습](08_DOCUMENT_INGESTION.md)에 따라 작은 가상 문서부터 등록하세요. 새 문서 등록을 반복하면 각각 다른 문서가 생깁니다. 이미 등록한 내용을 개정하려는 경우에는 목록에서 기존 문서를 선택합니다.

## 2. 문서 수정하기

1. 목록에서 등록 문서의 **수정**을 누르거나, 상세 화면에서 **문서·관계 수정**을 누릅니다.
2. 제목·본문·출처를 수정하고 **관계 다시 추출하기**를 누릅니다.
3. 새 미리보기에서 노드, 관계의 방향, 연결 대상, 근거 문장을 검토합니다. 빠진 관계를 추가하고 잘못된 관계는 수정하거나 제외합니다.
4. 검토 완료를 확인하고 **수정한 내용 저장하기**를 누릅니다.
5. 저장 성공 후 GraphRAG에서 해당 서비스를 다시 조회합니다.

**본문을 바꾸지 않고 관계만 고치는 경우**에는 저장된 관계를 불러와 수정할 수 있습니다. 원문이 그대로이므로 LLM을 다시 호출하지 않아도 됩니다. 제목·본문·출처 중 하나라도 바꾸면 기존 미리보기가 무효화되며 새 원문으로 추출해야 합니다.

예를 들어 문서 A의 이전 본문이 다음과 같다고 가정합니다.

```text
배송 서비스는 주문 서비스에 의존합니다. 배송 서비스는 물류팀이 담당합니다.
```

업무 변경을 반영해 본문을 다음과 같이 고칩니다.

```text
배송 서비스는 인증 서비스에 의존합니다. 배송 서비스는 물류팀이 담당합니다.
```

새 검토 결과에는 `배송 → 인증` 의존 관계를 포함하고 `배송 → 주문`은 제외합니다. 저장하면 문서 A의 이전 근거를 철회하고 새 근거를 기록합니다. `배송 → 주문`이 문서 등록으로 생성된 관계이며 다른 문서의 근거가 없다면 사라집니다. 다른 문서가 뒷받침하거나 예제·수동 관계이면 유지합니다.

수정 시 문서 ID는 유지됩니다. 문서 원문 갱신, 이전 근거 철회, 새 근거와 관계 저장은 하나의 트랜잭션입니다. 중간에 오류가 나면 변경 전 원문과 관계를 유지하므로 화면의 오류를 해결한 뒤 다시 시도합니다.

관계별 근거는 수정한 **본문에 실제로 들어 있는 문장**이어야 합니다. 노드·관계 종류, 입력 길이와 검증 규칙은 [문서 등록 가이드](08_DOCUMENT_INGESTION.md#3-노드와-관계-미리보기-확인하기)와 같습니다. 수정 후에도 문서에서 서비스로 향하는 `DESCRIBES` 관계가 최소 1개 필요합니다.

## 3. 문서 삭제하기

목록에서 등록 문서의 **삭제**를 누릅니다. 확인 화면에서 제목과 삭제 영향을 읽고 **삭제할 문서와 검색에 미치는 영향을 확인했습니다.**를 체크한 뒤 **문서 삭제하기**를 누릅니다. 삭제가 완료되면 해당 문서는 목록과 GraphRAG 출처에서 제외되고, 그 문서의 관계 근거도 제거됩니다.

문서 삭제는 서비스나 팀 자체를 지우는 작업이 아닙니다. 문서가 생성한 관계라도 다른 문서가 뒷받침한다면 유지합니다. 아래 표로 삭제 범위를 확인하세요.

| 대상 | 문서 삭제 후 처리 |
| --- | --- |
| 삭제한 문서의 제목·본문·출처 | DB에서 제거, 검색 출처에서 제외 |
| 해당 문서의 `DESCRIBES` 연결 | 제거 |
| 해당 문서의 관계 근거 `Assertion` | 제거 |
| 앱이 만들었고 다른 문서의 근거가 없는 관계 | 제거 |
| 다른 문서도 뒷받침하는 관계 | 유지 |
| 예제·수동 관계, 생성 경로를 확인할 수 없는 이전 관계 | 유지 |
| 서비스·팀 노드와 이름·설명 | 유지 |

현재 화면에는 삭제한 문서의 복원이나 버전 이력 열람 기능이 없습니다. 서버는 오래된 미리보기 요청이 문서를 되살리지 않도록 삭제한 ID·버전·시각만 별도로 남깁니다. 이 기록에는 원문을 보관하지 않습니다.

## 4. 관계가 사라지거나 남는 기준

문서 A와 B가 모두 `배송 서비스 → 주문 서비스`라는 의존 관계를 뒷받침하면, 업무 그래프의 관계는 하나이고 문서별 근거는 둘입니다. A를 삭제하거나 A의 검토 결과에서 해당 관계를 제외해도 B의 근거가 남으므로 의존 관계는 유지합니다. B의 근거도 철회하고 이 앱이 만든 관계일 때 비로소 제거합니다.

기존 예제나 수동 작업으로 만든 관계에는 문서 외의 근거가 있을 수 있습니다. 문서 등록 시 이미 존재하던 관계를 재사용했다고 해서 그 관계를 해당 문서의 소유로 간주하지 않습니다. 문서를 삭제해도 이런 관계는 남습니다.

이번 관리 기능부터 앱이 새로 만든 관계에는 `managed_by_documents=true`라는 표시를 저장합니다. 이전 버전은 관계의 생성 경로를 기록하지 않았으므로, 표시가 없는 관계가 문서에서 처음 만들어졌는지 기존 관계였는지 확정할 수 없습니다. 이런 관계는 경고와 함께 보존합니다. 운영자가 출처를 확인하지 않은 상태에서 일괄 삭제하거나 관리 표시를 붙이지 마세요.

서비스의 담당팀도 같은 규칙을 따릅니다. 이번 문서만 뒷받침하던 앱 관리 관계라면 수정 과정에서 이전 팀 관계를 철회할 수 있습니다. 다른 문서나 기존 그래프가 이전 담당팀을 뒷받침하면 새 팀과 충돌하므로 저장을 거부합니다. 이 경우 남은 근거부터 확인해야 합니다.

서비스·팀의 이름과 설명은 재사용하는 기본 정보이므로 문서를 수정·삭제해도 유지합니다. 잘못된 기본 정보를 고치려면 별도의 관리 작업이 필요합니다. 문서가 사라진 뒤 서비스가 목록에 남는 것은 정상입니다.

문서 등록·수정 과정에서 새로 만든 노드 설명은 `description_source='document'`로 구분합니다. 이 설명은 관리 화면에서 볼 수 있지만 GraphRAG의 사실이나 LLM 입력에는 포함하지 않습니다. 오래된 요약이 철회한 관계를 다시 답변에 섞지 않도록 현재 문서 원문과 관계를 근거로 사용합니다. 예제 데이터의 서비스 설명은 별도의 기준 정보로 유지합니다.

## 5. GraphRAG 반영 확인하기

GraphRAG는 검색 요청마다 Neo4j의 현재 그래프와 문서 원문을 읽습니다. 문서 수정·삭제 뒤에는 임베딩 생성이나 검색 인덱스 재구축을 기다릴 필요가 없습니다.

관리 화면에서 변경을 저장한 뒤 GraphRAG에서 해당 서비스를 선택하고 **근거만 조회**를 실행합니다. 다음 항목을 확인하세요.

- 수정한 제목과 본문이 출처에 표시되는지 확인합니다.
- 철회한 관계가 위 보존 규칙에 맞게 제거되거나 유지되는지 확인합니다.
- 삭제한 문서가 출처 목록에서 빠졌는지 확인합니다.
- 의존 관계를 바꿨다면 문맥 조회와 영향 분석 결과도 다시 확인합니다.

같은 브라우저에서 같은 주소·포트로 연 GraphRAG 탭은 문서 변경 알림을 받으면 이전 답변·근거·출처·Cypher 표시를 비우고, 그래프·서비스 목록과 최근 검색을 갱신합니다. 변경 전에 시작한 답변 생성이 뒤늦게 완료되어도 그 이전 결과를 다시 표시하지 않습니다. `localhost`와 `127.0.0.1`, 서로 다른 포트는 별개 주소이므로 자동 알림이 공유되지 않습니다.

이미 생성한 LLM 답변은 이전 검색 근거를 바탕으로 한 결과입니다. 최신 근거를 조회한 후 **답변 생성**을 다시 실행해야 새 답변을 받을 수 있습니다. 변경 알림이나 화면 갱신은 LLM 답변을 자동으로 새로 생성하지 않습니다. 다른 기기·브라우저에서 관리했다면 GraphRAG를 새로고침하고 다시 조회하세요.

삭제한 문서와 같은 사실을 다른 문서나 남은 관계가 계속 뒷받침하면 새 답변에도 그 사실이 나올 수 있습니다. 이는 삭제한 문서가 검색에 남았다는 뜻은 아닙니다. 출처 문서 ID와 관계 근거를 함께 확인합니다.

## 6. 동시에 수정했을 때

문서 상세를 불러오면 현재 `version`이 함께 전달됩니다. 수정 미리보기에는 그 버전을 서명하여 담고, 삭제 요청에도 버전을 보냅니다. 저장 직전에 DB 버전과 비교하므로 다른 창에서 먼저 수정한 문서를 오래된 내용으로 덮어쓰지 않습니다.

`409` 충돌이 나오면 미저장 원문이나 수정 내용을 별도로 보관한 뒤 최신 문서를 다시 불러오세요. 최신 내용을 기준으로 수정·검토합니다. 이전 토큰을 반복해서 보내 충돌을 해결할 수는 없습니다. 문서가 삭제되었다면 이전 초안으로 다시 저장할 수 없습니다.

미리보기의 유효기간은 등록 때와 같은 1시간입니다. 만료·서명 오류 시 원문을 보관하고 최신 문서를 다시 불러오거나 재추출합니다. 서버를 재시작할 때마다 오류가 난다면 `.env`의 `DJANGO_SECRET_KEY` 설정을 확인합니다.

## 7. 개발자를 위한 API

모든 변경 요청은 `Content-Type: application/json`과 CSRF 토큰이 필요합니다. `<document_id>`에는 목록·상세에서 받은 실제 문서 ID를 사용합니다.

| 메서드·경로 | 역할 |
| --- | --- |
| `GET /documents/manage/` | 문서 목록·관리 화면 |
| `GET /documents/?edit=<document_id>` | 기존 문서·관계 수정 화면 |
| `GET /api/documents/?q=&offset=0&limit=50` | 문서 목록 검색·페이지 조회 |
| `GET /api/documents/<document_id>/` | 원문·현재 관계·수정용 미리보기 조회 |
| `POST /api/documents/<document_id>/extract/` | 변경할 원문에서 관계 재추출 |
| `POST /api/documents/<document_id>/update/` | 검토한 원문·관계로 교체 |
| `POST /api/documents/<document_id>/delete/` | 문서 삭제와 근거 철회 |

목록 응답에는 `documents`, `total`, `offset`, `limit`, `has_more`가 있습니다. `limit`은 최대 100입니다. 각 문서의 `can_manage`로 수정·삭제 가능 여부를 구분하며 예제 문서는 `false`입니다. 상세 응답은 `document`, `nodes`, `relations`, `warnings`, `review_token`을 제공합니다. `document.version`은 클라이언트가 계산하거나 고치지 않고 받은 값을 유지합니다.

원문 재추출 요청 예시:

```json
{
  "version": "상세 응답의 document.version",
  "title": "배송 서비스 운영 안내 개정",
  "body": "배송 서비스는 인증 서비스에 의존합니다. 배송 서비스는 물류팀이 담당합니다.",
  "source": "internal-docs/delivery-guide"
}
```

수정 요청은 상세 조회 또는 재추출 응답의 `review_token`과 검토한 `nodes`, `relations`를 전달합니다. 본문을 수정했다면 반드시 재추출 응답의 토큰을 사용합니다. 서버는 토큰의 문서 ID·원본 버전·원문과 요청 경로를 검증합니다.

삭제 요청 예시:

```json
{"version": "상세 응답의 document.version"}
```

잘못된 입력은 `400`, 없는 문서는 `404`, 동시 수정이나 관계 충돌·읽기 전용 문서 변경은 `409`, DB·LLM 연결 실패는 `503`을 반환합니다. 동일한 버전으로 이미 성공한 삭제를 재시도해도 중복 작업 없이 성공 응답을 받습니다. 삭제된 문서의 오래된 수정·등록 미리보기는 다시 저장할 수 없습니다. JSON 응답은 브라우저·프록시에 저장하지 않도록 `Cache-Control: no-store`를 사용합니다.

## 8. 사내 서비스에 연결할 때

현재 관리 화면은 로그인 없는 로컬 실습용입니다. 사내 Django의 사용자 인증과 문서별 조회·수정·삭제 권한을 연결해야 합니다. 지금 구현한 버전 충돌 검사와 관계 근거 보존 정책은 권한 검사를 대신하지 않습니다.

사내 문서의 승인 절차, 보존 기간, 변경 이력, 복원, 감사 로그는 별도로 정합니다. PDF/DOCX 파싱이나 파일 저장소 동기화도 현재 범위에 포함하지 않습니다. 이 화면에서 출처를 바꿔도 원본 파일이나 사내 위키를 수정하지 않습니다.
